# Gateway API conformance

The `Gateway API conformance` job of the CI `e2e` workflow (`scripts/conformance.sh`) runs the Gateway API v1.7.0 conformance tests on kind (since v0.4.22, as the tests of the features added in v1.7 are only in the v1.7 suite; v1.6.3 before; the weekly compatibility run covers the older versions; rproxy built from rproxy-api master). Gateway API's CRDs are the experimental channel (`experimental-install.yaml`): some claimed features (`HTTPRouteRule.retry` of `HTTPRouteRetry*`) are experimental fields, which the API server drops with the standard CRDs. The report is the job's artifact (`conformance-report`) and its summary. The latest report: [../conformance/report.yaml](../conformance/report.yaml).

## The report from the released artifacts (for submission to Gateway API)

The badge (Conformant) in Gateway API's implementations list comes from a report submitted to kubernetes-sigs/gateway-api under `conformance/reports/<v1.x>/<organization>-<project>/`. That report is made from the released chart and images (nothing is built here): running the `e2e` workflow by hand with `report_version` (`gh workflow run e2e.yml -f report_version=0.4.12 -f report_gateway_api=v1.6.3`; upstream takes reports per Gateway API minor, so `report_gateway_api` picks the version, and `-f report_require=core` is for an older suite whose extended expectations changed later) runs only the `conformance report (published)` job, `scripts/conformance-report.sh`. It installs Gateway API v1.6.3's experimental-channel CRDs on kind, installs `oci://ghcr.io/max3584/charts/rproxy-gateway` at that version (default images, `managed.serviceType=ClusterIP`, `managed.addressCIDRs={192.0.2.0/24}`) and runs the Gateway API v1.6.3 suite with the five profiles. The claimed features are not passed with `--supported-features`: the suite reads them from the GatewayClass's `status.supportedFeatures` that the controller writes. The artifact `conformance-report-v<version>-<Gateway API version>` holds the report as the suite wrote it (`experimental-v<version>-default-report.yaml`), the suite's and the controller's logs and the environment (versions, image digests). The job succeeds only when every profile is core and extended success with no skipped test.

## Claimed features (`supportedFeatures`)

core (Gateway, HTTPRoute, ReferenceGrant, TLSRoute, TCPRoute, UDPRoute) plus `GatewayPort8080`, `GatewayHTTPListenerIsolation`, `HTTPRouteMethodMatching`, `HTTPRouteQueryParamMatching`, `HTTPRouteResponseHeaderModification`, `HTTPRoutePortRedirect`, `HTTPRouteSchemeRedirect`, `HTTPRoutePathRedirect`, `HTTPRoutePathRewrite`, `TLSRouteModeTerminate`, `TLSRouteModeMixed`, `HTTPRouteParentRefPort`, `HTTPRouteDestinationPortMatching`, `HTTPRouteNamedRouteRule`, `HTTPRouteBackendProtocolWebSocket`, `HTTPRouteBackendTimeout`, `GatewayStaticAddresses`, `GatewayAddressEmpty`, `GatewayInfrastructure`, `HTTPRoute303RedirectStatusCode`, `HTTPRoute307RedirectStatusCode`, `HTTPRoute308RedirectStatusCode`, `HTTPRouteRequestTimeout`, `HTTPRouteHostRewrite`, `HTTPRouteBackendRequestHeaderModification`, `HTTPRouteBackendURLRewrite` (v0.4.22: URLRewrite on a backendRef; the v1.7.0 suite has its test. Gateway API leaves undefined what a URLRewrite on both the rule and a backendRef does; in rproxy-gateway the server's middlewares run after the route's, so the backendRef's path rewrite applies last), `HTTPRouteCORS`, `HTTPRouteRetry`, `HTTPRouteRetryBackendTimeout`, `HTTPRouteRetryConnectionError`, `HTTPRouteRequestMirror`, `HTTPRouteRequestMultipleMirrors`, `HTTPRouteRequestPercentageMirror`, `HTTPRouteBackendProtocolH2C`, `GatewayFrontendClientCertificateValidation`, `GatewayFrontendClientCertificateValidationInsecureFallback`, `ListenerSet`, `GRPCRoute`, `GRPCRouteNamedRouteRule`, `BackendTLSPolicy`, `BackendTLSPolicySANValidation`, `GatewayBackendClientCertificate`, `GatewayHTTPSListenerDetectMisdirectedRequests` (v0.4.5), `GatewayRouteHostnameIntersectionPrecedence`, `HTTPRouteRetryCodes`, `GRPCRouteRequestHeaderModifier` (v0.4.22; Gateway API v1.7 names. `HTTPRouteRetryCodes` is the name the `HTTPRouteRetry` tests require since v1.7 (v1.7 no longer has `HTTPRouteRetry` or `HTTPRouteRetryBackendTimeout`; they stay claimed, as the suites up to v1.6 pick their tests by them) and uses rproxy's `retry` `status` (`retry_status` in `http_options`); `GRPCRouteRequestHeaderModifier` claims what GRPCRoute's `RequestHeaderModifier` already did, the same as HTTPRoute's), `HTTPRouteExternalAuth`, `HTTPRouteExternalAuthHTTP`, `HTTPRouteExternalAuthGRPC`, `HTTPRouteExternalAuthForwardBody` (v0.4.5; neither Gateway API v1.6.3's nor v1.7.0's conformance has these names or tests, so they do not show in the report; they are tested by `tests/rproxy.rs` against a real rproxy, unit tests and rproxy-api's `tests/ext_authz.rs`). `ClusterTrustBundle` (v0.4.22, GEP-5075): `caCertificateRefs` of BackendTLSPolicy and of the Gateway's client certificate validation can name a ClusterTrustBundle (`group: certificates.k8s.io`, `kind: ClusterTrustBundle`), with no ReferenceGrant. It is in the GatewayClass's `supportedFeatures` only while the API server serves ClusterTrustBundles (`certificates.k8s.io/v1` in Kubernetes 1.37; earlier only with the beta API enabled); otherwise a reference is `InvalidKind` (`InvalidCACertificateKind` on a Gateway). A missing, empty or non-PEM bundle is `InvalidCACertificateRef`. The controller's ClusterRole gets get, list and watch on `clustertrustbundles`. The v1.7.0 suite has no test for it yet; unit tests and the e2e (kind, Kubernetes 1.37: client certificates checked, `InvalidCACertificateRef` once the bundle is deleted) cover it. `GatewayAddressRoutability` and `GatewayAddressRoutabilityCluster` (v0.4.22, GEP-5093: `spec.addresses[].routability`). Empty is as before (the Service's external addresses, else its ClusterIP; static addresses as `externalIPs`). Each `Cluster` entry gets a ClusterIP Service of its own in the Gateway's namespace. A value (a given ClusterIP) is allowed only where the GatewayClass's parameters set `policy.clusterIPs: true`, and is not assigned by default; the API server refuses a value outside the ServiceCIDR or already taken, and that entry is left unassigned. When every entry is `Cluster`, the Gateway's own Service is ClusterIP too. `testing.x-k8s.io/sentinel` is served like `Cluster` (a default address in the fleet); other prefixed values are not assigned. The fleet assigns no `Cluster` entry, so only managed classes claim `GatewayAddressRoutabilityCluster`. `status.addresses` has one address per entry with `routability` (`Cluster` for a ClusterIP, else empty), and the Gateway gets `AddressesAssigned` (`AddressesAssigned`, `PartiallyAssigned`, `NotAssigned`). The v1.7.0 suite has no test for it yet, so `scripts/routability.sh` in the conformance job checks the GEP's scenarios. Details: [PLATFORM.md](PLATFORM.md). `GatewayStaticAddresses` runs with `--usable-address=192.0.2.10` and `--unusable-address=0.0.0.0`. The GatewayClass `status.supportedFeatures` and `FEATURES` of `scripts/conformance.sh` are the same (a unit test checks; `GatewayListenerFilters` depends on the rproxy, which the conformance job's, built from rproxy-api master, has). `GatewayListenerFilters` (v0.4.22, GEP-5224): a listener's `filters.requests` become rproxy v0.4.22's `http.pre_routing`, so `ExternalAuth` and RproxyMiddleware `ExtensionRef` filters run in the listener's order before route matching. It is used only when every rproxy pod of the Gateway answers `pre_routing` in `http_options`; otherwise the listener gets `Accepted: False` (`UnsupportedValue`) and its host name stays out of the port's other listeners. Listeners of one port whose filters differ: the ones with filters are not accepted. The GatewayClass claims it only once its rproxy is known to have it (the bundled rproxy v0.4.21 does not). The v1.7.0 suite has no test for it yet; `scripts/listener-filters.sh` in the conformance job and `tests/rproxy.rs` against a real rproxy cover it. Details: [DESIGN-v0.4.x.md](DESIGN-v0.4.x.md) 17. The newer HTTPRoute features need the `features` of rproxy v0.4.0 (docs/en/DESIGN.md, "rproxy features"). The features claimed in v0.4.5 and the `CORS`, `RequestRedirect`, `RequestMirror` and `ExternalAuth` filters on backendRefs need rproxy v0.4.3's `features` (`misdirected` in `http_options`, `server_middleware_kinds`, `forward_auth`).
